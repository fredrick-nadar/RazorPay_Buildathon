# 2. Mission

Build a working financial flight recorder that:

1. imports synthetic payment, refund, settlement, bank, and ledger records;
2. preserves source provenance and validates every row;
3. reconciles straightforward records deterministically;
4. turns residual discrepancies into typed cases;
5. renders a typed evidence graph;
6. uses one bounded AI investigator only for residual cases;
7. requires competing hypotheses and structured evidence;
8. verifies explanations with deterministic code;
9. creates machine-readable proof packages;
10. previews the internal ledger effect;
11. requires approval for every nonzero correction;
12. applies only a simulated adjustment entry;
13. leaves ambiguous cases unresolved;
14. records an append-only audit trail;
15. demonstrates duplicate/out-of-order event recovery;
16. runs a frozen holdout benchmark with honest metrics;
17. supports a reliable five-minute demo.

The mandatory exception classes are exactly:

- `DUPLICATE_LEDGER_POSTING`
- `MISSING_REFUND_POSTING`
- `SETTLEMENT_TIMING_WINDOW_SHIFT`
- `AMBIGUOUS_EVIDENCE`

Do not add exception classes until the final mandatory benchmark passes.

# 3. Product Principle

> **Use rules for calculation, AI for investigation, verification for closure, approval for authority, and humans for ambiguity.**

The model is not the accounting engine. It may inspect structured evidence, propose hypotheses, select deterministic tools, and explain results. It may not calculate authoritative totals, access labels, resolve a case directly, approve a correction, or mutate ledger data.

---

# 4. Hard Rules

1. Store INR as signed integer paise.
2. Never use binary floating-point money arithmetic.
3. Preserve immutable source rows and provenance.
4. Keep source event time, settlement time, import time, and accounting date distinct.
5. Make imports, runs, approvals, and simulated application idempotent.
6. Never silently drop an input row.
7. Ground-truth labels are evaluator-only and unreachable from runtime code.
8. The model cannot execute arbitrary code or SQL.
9. The model cannot call approval, application, ledger-write, or direct-resolution tools.
10. Every resolution requires deterministic verifier `PASS`.
11. Every passing proof cites existing evidence IDs and rule versions.
12. Every nonzero ledger delta requires human approval in the MVP.
13. Apply a correction by adding a linked simulated entry; never edit an imported row.
14. If evidence is non-unique, return `UNRESOLVED`.
15. A confidence score cannot override missing evidence or failed constraints.
16. Imported text is untrusted data and cannot provide agent instructions.
17. A model timeout, malformed response, or provider error cannot change financial state.
18. No real money moves.
19. No production ERP is written.
20. Only documented Razorpay Test Mode/public read APIs may be used.
21. Do not invent APIs, policies, integrations, measured results, or platform access.
22. Demo authority values are labelled synthetic merchant policy.
23. Do not claim reconciliation proves fraud absence, compliance, or source truth.
24. Do not claim to trace a physical rupee; trace the evidence path behind recorded amounts.
25. Never publish a benchmark number that was not generated by code.
26. Do not hide failed or unresolved cases from evaluation denominators.
27. Do not add Redis, pgvector, RAG, distributed workers, realtime voice, or extra agents to the mandatory path.
28. Keep the rules-only system usable when no model key is configured.
29. Keep the demo usable without animation or speech.
30. Do not proceed to the next phase when a mandatory acceptance gate fails.

# 5. Required Architecture

Use the smallest reliable implementation that satisfies the PRD.

Recommended structure:

```text
frontend: Next.js + React + TypeScript + Tailwind
backend: FastAPI + Python + Pydantic
persistence: SQLite by default behind repository interfaces
tests: pytest, targeted Hypothesis properties, frontend unit tests, Playwright E2E
AI: configurable structured-output provider plus deterministic fake provider

```

PostgreSQL may be supported later through the persistence interface, but it is not required for the local submission. Polling is acceptable; add SSE only if it is simpler than the current alternative.

The deterministic verifier is code. It is not another agent.
